# Планы развития Yevqo

Этот документ — актуальная дорожная карта Yevqo. Он описывает состояние реализации и оставшиеся задачи, а не обещает сроки. Отметка «готово» означает, что соответствующая часть реализована в коде; физическая проверка на Android отдельно отмечается как незавершённая.

Yevqo в первую очередь рассчитан на Android и Termux. Не следует считать Docker, Nixpacks или Railpack доступными непосредственно в Termux: для них потребуется отдельный совместимый Linux-исполнитель.

## P0 — Надёжная работа приложений

### Реализовано

- [x] Постоянный реестр процессов сайтов: PID, группа процессов, среда выполнения, порт, рабочая директория и время запуска.
- [x] Проверка идентичности процесса после перезапуска Agent; защита от отправки сигналов процессу с повторно использованным PID.
- [x] Корректная остановка группы процессов: SIGTERM, ожидание и SIGKILL при необходимости.
- [x] Отслеживание завершения процессов, сбор дочерних процессов и отображение причин аварийного завершения.
- [x] Политики перезапуска: `never`, `on-failure`, `always`; ограниченные повторные попытки с увеличением задержки.
- [x] Проверка готовности TCP и необязательная HTTP-проверка для Git-деплоев.
- [x] Сбор stdout/stderr, ограниченная ротация логов, потоковый просмотр, временные метки, поиск и фильтры.
- [x] Этапы деплоя, прогресс, отмена и ограничение одним активным деплоем на сайт.
- [x] Запуск PHP, Go, статических сайтов, Node.js и пользовательских сред через явно заданную команду.
- [x] Сборка Git-релиза во временной директории до переключения трафика.
- [x] Неизменяемые релизы, откат к предыдущей версии и восстановление после прерванного переключения.
- [x] Стабильный reverse-proxy порт с blue-green переключением: новая версия проверяется до перенаправления трафика.
- [x] Привязка публичного listener сайта к `0.0.0.0`, чтобы сайт был доступен не только через localhost, но и через сетевые интерфейсы телефона. Внутренний backend приложения остаётся на `127.0.0.1`.
- [x] Тесты жизненного цикла, восстановления, переключения релизов, проверки здоровья и сетевой привязки listener.

### Ограничения

- Автоматические перезапуски ограничены, чтобы приложение не попадало в бесконечный цикл падений.
- Android может завершать фоновые процессы из-за энергосбережения, принудительной остановки или ограничений ОС. Yevqo не может гарантировать работу после force-stop без корректной фоновой настройки.
- Публичные порты, слушающие все интерфейсы, доступны устройствам, которые могут подключиться к телефону по сети. Используйте доверенную сеть и учитывайте правила firewall/роутера.

## Модель выполнения приложений в Termux

Yevqo использует нативные процессы, а не Docker-контейнеры на Android:

- Agent управляет реестром процессов и отслеживает дочерние процессы.
- У каждого приложения отдельные рабочая директория, переменные окружения, группа процессов и поток логов.
- PID сам по себе не считается надёжной идентичностью процесса.
- После перезапуска Agent сверяет сохранённое состояние с реальными процессами.
- Логи хранятся на устройстве и передаются в Control Plane.
- Ограничения фоновой работы Android должны быть явно показаны пользователю.

## План проверки совместимости и качества

Для каждого важного сценария нужно фиксировать результат, а не считать его работающим только по наличию интерфейса или кода.

1. Создать тестовый сайт из Git-репозитория.
2. Выполнить деплой и проверить логи, commit и активный релиз.
3. Открыть сайт на самом телефоне.
4. Открыть сайт с другого устройства в той же локальной сети.
5. Проверить доступ через настроенный домен и Cloudflare Tunnel.
6. Перезапустить Agent и проверить восстановление сайта.
7. Выполнить повторный деплой и откат.
8. Проверить остановку, запуск и поведение после ошибки сборки.

Для сравнения с Dokploy использовать один и тот же тестовый репозиторий, ветку, команду сборки и health endpoint. Сравнивать время до первого успешного ответа, количество ручных действий, понятность ошибок и восстановление после сбоя. Не объявлять победителя без реального тестирования обеих систем.

## Правила ведения дорожной карты

- Обновлять этот файл при реализации или изменении статуса задачи.
- Не отмечать задачу выполненной только потому, что добавлен макет или API-заглушка.
- Разделять «реализовано в коде», «CI прошёл» и «проверено на Android».
- Не обещать сроки без согласованного плана работ.
- Все изменения проекта выполнять только в ветке `main`.
